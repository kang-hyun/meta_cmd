# KETI 모바일 베이스 통신 프로토콜 설명서

| 항목 | 내용 |
|---|---|
| 대상 장치 | KETI 모바일 베이스(리프트 없음), 펌웨어 `mobile_keti` |
| 문서 기준 | 2026-11 판 펌웨어(소스 커밋 `1f75b64`, 프레임 라이브러리 `3afc016`) |
| 작성일 | 2026-11-09 |
| 이전 납품본 | 2026-08 납품 펌웨어(`e118888`). 달라진 점은 [7절](#7-이전-납품본2026-08과-달라진-점) |

## 1. 개요

- 호스트(PC)와 펌웨어(ESP32)는 USB 시리얼 하나로 바이너리 패킷을 주고받는다.
- 펌웨어는 바퀴 속도 제어(PID + feed-forward), 모터 드라이버 구동, 명령이 끊겼을 때의 정지를 맡는다.
- 호스트는 바퀴 목표 각속도를 계산해 주기적으로 보내고, 바퀴 상태를 받는다.
- 시리얼 포트는 프로그램 하나만 연다. 두 프로그램이 같은 포트에 쓰면 명령이 섞인다.
- 속도 변환에 쓰는 차체 값: 바퀴 반경 **0.155 m**, 좌우 바퀴 간격 **0.60 m**.

## 2. 연결

| 항목 | 값 |
|---|---|
| 회선 | USB 시리얼(ESP32 UART0) |
| 속도 | **500000 baud**, 8N1 |
| 내용 | 바이너리 패킷만. 텍스트 출력 없음 |
| USB-시리얼 칩 | 500000 baud를 지원해야 한다(CP210x, CH340 지원) |
| 버전 조회 | 장치에서 펌웨어 버전을 조회하는 명령은 없다. 펌웨어 판은 납품 기록으로 확인한다 |

## 3. 프레임 형식

```text
[0xFF 0xF9] [len] [id] [ack] [count] [field 1] … [field N] [crc]
              │                        └─ field = [type][size][value]
              └─ id 부터 마지막 field 까지의 byte 수. 프레임 전체 길이 = len + 4
```

| 위치 | 크기 | 의미 |
|---|---|---|
| 0–1 | 2 B | 헤더 `0xFF 0xF9` |
| 2 | 1 B | `len`: `id`부터 마지막 field까지의 byte 수 |
| 3 | 1 B | 패킷 ID([4절](#4-패킷-목록)) |
| 4 | 1 B | `ack`: `0` NO_ACK(응답 없음), `2` ACK(응답 요청), `3` RES(응답) |
| 5 | 1 B | field 개수 |
| 6– | 가변 | field 들. 각 field는 `[type 1 B][size 1 B][value]` |
| 끝 | 1 B | 체크섬 |

- field 타입: `0` = i32(4 B), `1` = f32(4 B), `2` = f64(8 B). 모든 값은 **little endian**이다.
- 응답(RES)은 요청과 같은 ID에 data가 없는 7 B 프레임이다(예: `0x03`의 응답 `ff f9 03 03 03 00 13`).
- 가장 긴 프레임은 `0x03`(97 B)이다.
- **체크섬**: 체크섬 byte를 뺀 프레임 전체(헤더 포함)에 대해 계산한다. 초기값 `0xFF`, byte마다 XOR한 뒤 8번 오른쪽으로
  shift하며, shift 전 최하위 bit가 1이면 `0x1D`와 XOR한다. 마지막 XOR은 없다.
- **수신 규칙**: 헤더를 찾아 `len + 4` byte를 모은 뒤 체크섬이 맞으면 받아들인다. 틀리면 1 byte만 버리고 다시 헤더를 찾는다.
- 펌웨어는 모르는 패킷 ID를 무시한다.

예: `0x02` MOTOR_SPEED, 좌 1.5 rad/s, 우 −2.25 rad/s (27 B)

```text
ff f9 | 17 | 02 | 00 | 02 | 02 08 00 00 00 00 00 00 f8 3f | 02 08 00 00 00 00 00 00 02 c0 | 11
헤더   len  id   ack  개수  f64  1.5                         f64  -2.25                       crc
      (23)      NO_ACK
```

## 4. 패킷 목록

| ID | 이름 | 방향 | ack | payload | 크기 | 응답 |
|---|---|---|---|---|---|---|
| `0x01` | MOTOR_STATE | 펌웨어 → 호스트 | NO_ACK | f64 × 6 | 67 B | — |
| `0x02` | MOTOR_SPEED | 호스트 → 펌웨어 | NO_ACK | f64 × 2 | 27 B | 없음 |
| `0x03` | MOTOR_CONFIG | 호스트 → 펌웨어 | ACK | i32 + f32 × 14 | 97 B | RES (7 B) |
| `0xFF` | MOTOR_RESET | 호스트 → 펌웨어 | ACK | 없음 | 7 B | RES (7 B) |

### 0x01 MOTOR_STATE (50 Hz)

| 순서 | 타입 | 값 | 단위 |
|---:|---|---|---|
| 1 | f64 | 왼쪽 바퀴 속도 | rad/s, 전진 + |
| 2 | f64 | 왼쪽 PWM 크기 | 0 ~ 1 |
| 3 | f64 | 왼쪽 위치 | rad, 부팅 후 누적 |
| 4 | f64 | 오른쪽 바퀴 속도 | rad/s, 전진 + |
| 5 | f64 | 오른쪽 PWM 크기 | 0 ~ 1 |
| 6 | f64 | 오른쪽 위치 | rad, 부팅 후 누적 |

### 0x02 MOTOR_SPEED

| 순서 | 타입 | 값 | 단위 |
|---:|---|---|---|
| 1 | f64 | 왼쪽 바퀴 목표 각속도 | rad/s, 전진 + |
| 2 | f64 | 오른쪽 바퀴 목표 각속도 | rad/s, 전진 + |

- 좌우 모터의 회전 방향 반전은 펌웨어가 처리한다. 호스트는 두 바퀴 모두 "전진 +"로 보낸다.
- **250 ms 안에 다시 보내야 한다.** 권장 주기는 20 Hz다([6절](#6-시간-제한과-전송량)).
- `cmd_vel`(선속도 v, 각속도 ω)에서 바꿀 때: 왼쪽 = (v − ω × 0.60 / 2) / 0.155, 오른쪽 = (v + ω × 0.60 / 2) / 0.155.

### 0x03 MOTOR_CONFIG

한 바퀴의 제어 게인을 바꾼다. 받으면 즉시 적용하고 그 바퀴의 제어기를 리셋(목표 0)한 뒤 RES로 답한다. 저장하지 않으므로
재부팅하면 아래 기본값으로 돌아간다.

| 순서 | 타입 | 이름 | 단위 | 기본값(왼쪽) | 기본값(오른쪽) |
|---:|---|---|---|---:|---:|
| 1 | i32 | motor | 0 = 왼쪽, 1 = 오른쪽 | — | — |
| 2 | f32 | KP | | 0.008 | 0.008 |
| 3 | f32 | KI | | 0.0 | 0.0 |
| 4 | f32 | KD | | 0.0 | 0.0 |
| 5 | f32 | KF | | 0.063 | 0.065 |
| 6 | f32 | PWM_MAX | | 1.0 | 1.0 |
| 7 | f32 | W_STOP_REF | rad/s | 0.05 | 0.05 |
| 8 | f32 | W_CRAWL_REF | rad/s | 1.0 | 1.0 |
| 9 | f32 | W_MEAS_DEADBAND | rad/s | 0.03 | 0.03 |
| 10 | f32 | W_HOLD | rad/s | 0.03 | 0.03 |
| 11 | f32 | I_MAX_RUN | | 0.20 | 0.20 |
| 12 | f32 | I_MAX_CRAWL | | 0.10 | 0.10 |
| 13 | f32 | U_STATIC_FWD | | 0.007 | 0.007 |
| 14 | f32 | U_STATIC_REV | | 0.012 | 0.012 |
| 15 | f32 | REF_ACC_LIMIT | rad/s² | 24.516 | 24.516 |

`REF_ACC_LIMIT` 기본값은 선속도 가감속 3.8 m/s²를 바퀴 반경 0.155 m로 나눈 값이다.

### 0xFF MOTOR_RESET

data 없이 ACK로 보낸다. 펌웨어는 휠 목표를 0으로 만들고 명령 감시(watchdog)를 끈 뒤, 모터 드라이버에 정지 프레임을 보내고
CAN을 끊은 다음 RES로 답한다. 모터 드라이버 재연결에 약 3초가 걸리며 그동안 속도 명령은 모터에 나가지 않는다.

## 5. 정지 방법

전용 비상정지 패킷은 없다. 바퀴를 세우는 방법은 네 가지다.

| 방법 | 호스트가 할 일 | 펌웨어 동작 | 다시 움직이려면 |
|---|---|---|---|
| **정상 정지** | `0x02`를 (0, 0)으로 보낸다 | 가감속 한계(3.8 m/s²)를 따라 감속하고, 감속 중인 목표가 0.05 rad/s 아래로 내려가면 PWM 0. 1 m/s에서 약 0.29 초 | 다음 `0x02`부터 바로 |
| **통신 끊김 정지**(자동) | — (마지막 `0x02` 후 250 ms 동안 아무것도 오지 않음) | 감속 없이 곧바로 목표 0, 제어기 리셋 | 다음 `0x02`부터 바로 |
| **리셋 정지** | `0xFF`를 ACK로 보내고 RES를 기다린다 | 목표 0, 감시 해제, 모터 드라이버 정지 프레임 후 CAN 분리 | 약 3초 뒤(CAN 재연결) |
| **하드웨어 스위치** | 제어 모드 스위치(`GPIO23`)를 HIGH로 | 모터 드라이버 분리 | 스위치를 LOW(펌웨어 구동)로 |

- 정지 중에는 같은 주기로 (0, 0)을 계속 보내면 된다. 보내지 않아도 250 ms 뒤 감시가 목표를 0으로 유지한다.
- 호스트 프로그램을 끝낼 때는 (0, 0)을 몇 번(예: 20 ms 간격 5회) 보내고 포트를 닫는다.
- 정지 뒤의 제동은 능동 브레이크가 아니다. "정지" 상태의 모터 드라이버 명령은 중립 + 페달 0으로 나가며, 그 뒤 감속 특성은
  모터 드라이버의 페달 해제 특성에 따른다.
- 10초 이상 정지해 있으면 펌웨어가 모터 드라이버 연결을 다시 맺는다. 그동안(약 3초) 출발 명령에 반응하지 않는다.

## 7. 이전 납품본(2026-08)과 달라진 점

프레임 형식, 패킷 ID, 각 패킷의 field 순서와 타입은 이전 납품본과 **같다**. 아래 항목은 바뀌었다.

| 항목 | 이전 납품본 | 현재 |
|---|---|---|
| baud | 115200 | **500000** |
| 펌웨어 루프 · `0x01` 송신 | 10 Hz | 50 Hz |
| 가감속 | 실효 0.78 m/s² | 3.8 m/s² |
| 1 m/s 정지 시간 | 약 1.33 초 | 약 0.29 초 |
| 명령이 끊기면 | 감지 없음(마지막 속도를 계속 유지) | **250 ms 뒤 정지** |
| `0xFF` | CAN만 끊고 목표 속도 유지 | 목표 0으로 만든 뒤 CAN 끊음 |
| `REF_ACC_LIMIT` 기본값 | 50.0 rad/s² | 24.516 rad/s² |

교체할 때 주의할 점:

- 호스트의 baud를 **500000**으로 바꿔야 통신된다. 115200으로 두면 프레임을 하나도 받지 못하고, 바퀴는 펌웨어 감시로 선다.
- 호스트가 `0x02`를 **250 ms보다 짧은 간격으로 계속** 보내야 한다. 값이 바뀔 때만 보내는 구현은 주행 중에 멈춘다.
- `0x01`이 초당 10개에서 50개로 늘어난다. 수신 처리 주기를 확인한다.
- 출발도 빨라진다(0.78 → 3.8 m/s²).
- 이전 납품 드라이버를 그대로 쓸 때는 `-p baudrate:=500000 -p wheel_radius:=0.155`를 준다(그 드라이버의 기본값은 115200, 0.12).
- 펌웨어와 호스트 프로그램은 함께 교체한다.

## 8. 호스트 구현 점검표

- [ ] 시리얼 500000 baud, 8N1로 연다. 포트는 한 프로그램만 연다.
- [ ] 수신은 헤더 탐색 → `len + 4` byte 수집 → 체크섬 확인 순서로 하고, 틀리면 1 byte 버리고 다시 찾는다.
- [ ] `0x02`를 20 Hz(최소 5 Hz)로 계속 보낸다. 정지 중에도 (0, 0)을 보낸다.
- [ ] 두 바퀴 모두 "전진 +" rad/s로 보낸다. 반경 0.155 m, 간격 0.60 m로 변환한다.
- [ ] `0x03`, `0xFF`는 ACK로 보내고 RES(7 B)를 기다린다. 응답이 없으면 다시 보낸다.
- [ ] `0xFF` 뒤 약 3초, 10초 이상 정지 뒤 약 3초는 출발하지 않는 것을 감안한다.
- [ ] 종료할 때 (0, 0)을 몇 번 보내고 포트를 닫는다.

## 9. 예시 코드 (Python)

아래 코드는 [10절](#10-검증용-프레임)의 프레임을 byte 단위로 그대로 만든다.

```python
import struct

HEADER = b"\xff\xf9"
NO_ACK, ACK, RES = 0, 2, 3
I32, F32, F64 = 0, 1, 2
_FMT = {I32: "<i", F32: "<f", F64: "<d"}


def checksum(data):
    crc = 0xFF
    for value in data:
        crc ^= value
        for _ in range(8):
            crc = (crc >> 1) ^ (0x1D if crc & 1 else 0)
    return crc & 0xFF


def encode(packet_id, ack, fields=()):
    """fields: [(type, value), ...] -> frame bytes"""
    body = bytes([packet_id, ack, len(fields)])
    for kind, value in fields:
        raw = struct.pack(_FMT[kind], value)
        body += bytes([kind, len(raw)]) + raw
    frame = HEADER + bytes([len(body)]) + body
    return frame + bytes([checksum(frame)])


def decode(buffer):
    """buffer 앞에서 frame 하나를 찾는다 -> ((id, ack, [values]), 남은 buffer) 또는 (None, buffer)"""
    while len(buffer) >= 7:
        if buffer[0:2] != HEADER:
            buffer = buffer[1:]
            continue
        total = buffer[2] + 4
        if len(buffer) < total:
            return None, buffer
        frame = buffer[:total]
        if checksum(frame[:-1]) != frame[-1]:
            buffer = buffer[1:]  # 체크섬이 틀리면 1 byte 버리고 헤더를 다시 찾는다
            continue
        values, index = [], 6
        for _ in range(frame[5]):
            kind, size = frame[index], frame[index + 1]
            values.append(struct.unpack(_FMT[kind], frame[index + 2:index + 2 + size])[0])
            index += 2 + size
        return (frame[3], frame[4], values), buffer[total:]
    return None, buffer


# 사용 예
speed = encode(0x02, NO_ACK, [(F64, 1.5), (F64, -2.25)])  # 20 Hz 로 계속 보낸다
stop = encode(0x02, NO_ACK, [(F64, 0.0), (F64, 0.0)])     # 정상 정지
reset = encode(0xFF, ACK)                                 # 리셋 정지, RES(ff f9 03 ff 03 00 1d)를 기다린다
```

## 11. 납품 드라이버(ROS 2)를 쓸 때

같이 납품하는 단일 파일 ROS 2 드라이버는 위 프로토콜을 구현한다.

| 파라미터 | 기본값 | 설명 |
|---|---:|---|
| `port` | `/dev/ttyUSB0` | 시리얼 장치 |
| `baudrate` | `500000` | 펌웨어와 같아야 한다 |
| `cmd_vel_topic` | `cmd_vel` | 속도 명령 토픽 |
| `motor_state_topic` | `motor_state` | 상태 토픽 |
| `wheel_radius` | `0.155` | 바퀴 반경 m |
| `wheel_separation` | `0.60` | 좌우 바퀴 간격 m |
| `control_rate` | `20.0` | `0x02` 송신 주기 Hz. 5 Hz 미만은 거부한다 |
| `cmd_vel_timeout` | `0.5` | 마지막 `cmd_vel` 후 0을 보내기까지의 시간 s |
| `max_wheel_speed` | `20.0` | 바퀴 목표 상한 rad/s. 넘는 명령은 무시 |

- `cmd_vel`이 끊기면 `cmd_vel_timeout` 뒤 0을 보내고, 드라이버나 USB가 끊기면 펌웨어가 250 ms 뒤 스스로 선다.
- 종료할 때(Ctrl-C, SIGTERM) 0 속도를 여러 번 보내고 종료 코드 0으로 끝난다.
- 통신 중 포트가 사라지면 정지 프레임을 시도한 뒤 종료 코드 1로 끝난다. 서비스로 운용하면 자동 재시작(systemd
  `Restart=on-failure` 등)에 맡긴다.

## 12. 확인 범위

- 확인한 것: 위 검증용 프레임 bytes(펌웨어·납품 드라이버·이전 납품 드라이버 일치), 정지 시간과 250 ms 감시(호스트 모의 검사),
  ESP32 컴파일, 이전 납품본과 프레임 형식·패킷 field가 같음.
- 실기에서 아직 확인하지 않은 것: 실제 정지 응답 시간, 500000 baud 통신.
